# LILY LOOK

Интернет-магазин женской одежды. SvelteKit 2 + Svelte 5 (runes), Tailwind v4, shadcn-svelte, Prisma 7, Neon Postgres.

Интерфейс магазина — на украинском. Комментарии в коде — тоже (совпадают с языком витрины).

---

## Быстрый старт

```bash
npm install
cp .env.example .env      # подставь строки подключения из console.neon.tech
npm run db:migrate        # создаст таблицы
npm run db:seed           # зальёт демо-каталог: 6 категорий, 14 товаров
npm run dev
```

Пока `DATABASE_URL` пустой, любой запрос ведёт на `/setup` с инструкцией — вместо стектрейса Prisma.

### Строки подключения Neon

В консоли Neon два варианта connection string. Нужны оба:

| Переменная     | Какой endpoint             | Для чего              |
| -------------- | -------------------------- | --------------------- |
| `DATABASE_URL` | pooled (в хосте `-pooler`) | Приложение в рантайме |
| `DIRECT_URL`   | direct (без `-pooler`)     | Миграции и сиды       |

Рядом с `src/` — остальное:

```
tests/     зеркало src/, см. tests/README.md
prisma/    схема, миграции, демо-данные
scripts/   разовые операции (регистрация вебхука бота)
static/    иконки и манифест — отдаются с корня домена
```

**Тесты лежат отдельно от кода.** Дерево `tests/` повторяет `src/` файл в файл: тест для `src/lib/server/catalog.ts` — это `tests/lib/server/catalog.test.ts`. Так в рабочих папках видно только код, а путь к тесту выводится из пути к модулю. Обращаются они через алиасы `$lib/…` и `$routes/…`, поэтому переезд файла не тянет за собой правку `../../..`.

### Ключевые решения

**Деньги — целые числа в копейках.** Никаких `Float` и `Decimal`: нет ошибок округления, нет конвертации при сериализации в SvelteKit. Форматирование живёт только в `money.ts`.

**Корзина серверная.** В httpOnly-куке лежит только `id` корзины; товары, цены и остатки всегда читаются из БД. Клиент не может подкрутить сумму, а корзина переживает перезагрузку и смену вкладки.

**Варианты, а не товары.** Остаток, SKU и цена привязаны к паре размер+цвет (`ProductVariant`). В корзину и заказ попадает вариант — иначе невозможно честно вести склад.

**Позиции заказа денормализованы.** `OrderItem` хранит снимок названия, цены и фото. Товар потом переименуют, подорожает или исчезнет — заказ останется исторически точным.

**Списание остатков атомарно.** В `orders.ts` условие `stock >= quantity` стоит прямо в `UPDATE`, вся операция — в одной транзакции. Два покупателя не купят последнюю вещь одновременно.

**Оплата — интерфейс, а не ветвление.** `payments.ts` описывает `PaymentProvider`; сейчас зарегистрирован один — `manual` (оплата при получении). Подключение Stripe или LiqPay = один новый файл с реализацией интерфейса и вызов `registerPaymentProvider()`. Остальной код не меняется.

**Формы работают без JavaScript.** Все мутации — SvelteKit form actions; `use:enhance` только убирает перезагрузку и показывает тост. Фильтры каталога — обычные ссылки, поэтому индексируются и ими можно поделиться.

## Витрина и CRM: контракт через базу

Сайт — только витрина. Товары, категории, остатки и скидки ведёт внешняя CRM, подключённая к той же базе. Сайт из каталожных таблиц **только читает**; пишет он лишь в `Cart`, `CartItem`, `Order`, `OrderItem`.

### Что пишет CRM

| Задача                            | Куда писать                                                                |
| --------------------------------- | -------------------------------------------------------------------------- |
| Новая категория                   | `Category` — обязательно с `imageUrl`, иначе плитка каталога без фото      |
| Новая модель                      | `Product` (`price` — базовая цена) + `ProductImage` + `ProductVariant`     |
| Характеристики модели             | `ProductAttribute` — свободные пары «название → значение»                  |
| Фото конкретного цвета            | `ProductImage.color` — строка из `ProductVariant.color`                    |
| Замеры размеров                   | `ProductMeasurement` — строка на размер: `ua`, `chest`, `sleeve`, `length` |
| Остаток размера                   | `ProductVariant.stock`                                                     |
| Порядок размеров и цветов         | `ProductVariant.position`                                                  |
| Убрать один размер/цвет           | `ProductVariant.isActive = false`                                          |
| Убрать модель с сайта целиком     | `Product.isActive = false`                                                 |
| Скидка на товар / категорию / всё | `Discount` + `DiscountProduct` / `DiscountCategory`                        |

### Фото по цветам

`ProductImage.color` связывает кадр с цветом варианта — **строкой, буква в букву** из `ProductVariant.color` («Чорний», не «чорний» и не «black»). Покупатель выбирает цвет на странице товара — галерея показывает кадры именно этого цвета.

- `color = NULL` — кадр общий: показывается при любом выбранном цвете (крой, ткань вблизи, бирка);
- если у цвета **нет ни одного своего** кадра, сайт показывает весь набор фото товара — лучше лишние кадры, чем пустая галерея. Так же ведут себя старые товары, где цвет ещё не проставлен;
- порядок внутри цвета — тот же `position`;
- опечатка в названии цвета страницу не ломает, но кадр «потеряется» — он не попадёт ни к одному цвету. Найти такие:

```sql
SELECT i.id, i.color
FROM "ProductImage" i
WHERE i.color IS NOT NULL
  AND NOT EXISTS (
    SELECT 1 FROM "ProductVariant" v
    WHERE v."productId" = i."productId" AND v.color = i.color
  );
```

Фото остальных цветов сайт подгружает в фоне, пока браузер свободен, — переключение цвета происходит без ожидания.

**Обложка карточки — это фото первого цвета в наличии, а не первое фото товара.** Правило одно на весь сайт (`src/lib/product-images.ts`): его применяют и галерея, и карточки в списках, и `og:image`, и разметка для Google. Иначе получается то, что было: у «Сукня-міді Amélie» чёрный разобрали, на карточке висела чёрная куртка, а по клику открывалась белая — потому что карточка брала фото по `position`, а страница открывала первый цвет **в наличии**.

Из этого следует требование к CRM: **чтобы обложка переключалась, у фото должен быть проставлен `color`.** Если у товара ни у одного кадра цвет не указан, сайт не знает, какие фото чьи, и показывает первое фото товара — как и раньше. Найти такие товары:

```sql
SELECT p.slug, p.name
FROM "Product" p
WHERE p."isActive"
  AND (SELECT count(DISTINCT v.color) FROM "ProductVariant" v WHERE v."productId" = p.id) > 1
  AND NOT EXISTS (
    SELECT 1 FROM "ProductImage" i WHERE i."productId" = p.id AND i.color IS NOT NULL
  );
```

### Порядок размеров и цветов

`ProductVariant.position` — чем меньше число, тем раньше вариант показывается. Порядок задаёт менеджер в CRM, сайт его только читает: сам он ничего не знает ни о том, что «Чорний» идёт перед «Білим», ни о том, что 3XL идёт после XXL.

Колонка создана с `DEFAULT 0`. Пока порядок не проставлен, у всех вариантов нули — тогда сайт падает на запасной ключ: размеры выстраиваются по шкале `SIZE_ORDER` из `config.ts`, а цвета и незнакомые шкале размеры (`One size`, 38–54) — по алфавиту. Это не «правильный» порядок, а лишь гарантия, что список не будет тасоваться между заходами.

Вариант — это пара «цвет + размер», а списков на странице два, поэтому сайт не берёт `position` напрямую:

- **цвета** — по минимальной позиции среди своих вариантов;
- **размеры** — по месту внутри своего цвета, а не по позиции.

Второе важно, потому что из сплошной нумерации не видно, что шло внешним циклом: цвета или размеры. Если нумеровать цветами (`Чорний XS, S, M`, потом `Білий XS, S, M`) и в чёрном нет XS, то по позиции XS уехал бы в конец списка — после L. Место внутри цвета даёт одинаковый ответ при обеих нумерациях.

**Распроданный цвет съезжает вниз — так задумано.** Порядок считается только по тем вариантам, которые реально можно купить. Если в CRM `Чорний / L` стоит первым, но его разобрали, то чёрный поедет за тем цветом, чей размер ещё в наличии. Это решение принято сознательно: список на странице — это список того, что можно положить в корзину, и порядок в нём считается по нему же. Чтобы порядок держался жёстко по CRM, пришлось бы читать со страницы и распроданные варианты — этого мы не делаем.

Фильтры каталога (`/catalog`) сортируются иначе — там список размеров и цветов общий на все товары, а `position` у каждого товара свой, так что сравнивать нечего: размеры идут по `SIZE_ORDER`, цвета по алфавиту.

### Таблица размеров

`ProductMeasurement` — по строке на размер товара: `size` (строка из `ProductVariant.size`), `ua`, `chest`, `sleeve`, `length`, `position`. **Таблицу ведёт CRM, сайт из неё только читает** — никакого справочника размеров в коде больше нет, поэтому в модалке стоят ровно те размеры, что записаны товару: хоть `S/M`, хоть `6XL`.

- `id` без значения по умолчанию — его генерирует тот, кто пишет строку;
- любой замер можно оставить пустым: колонка, пустая во **всех** строках товара, в таблице не рисуется (у юбки нет рукава). Пустая клетка в частично заполненной колонке показывается прочерком;
- порядок строк — `position`, как его задала CRM. Сайт не пытается угадать порядок сам: размеры бывают произвольные, и отсортировать `S/M` рядом с `6XL` нечем;
- **нет ни одной строки — на странице нет и ссылки «Таблиця розмірів»**. Показывать чужие замеры хуже, чем не показывать ничего;
- `size` сверяется с размерами вариантов только глазами: строка с размером, которого у товара нет, просто будет лишней в таблице. Найти такие:

```sql
SELECT m.id, m.size
FROM "ProductMeasurement" m
WHERE NOT EXISTS (
  SELECT 1 FROM "ProductVariant" v
  WHERE v."productId" = m."productId" AND v.size = m.size
);
```

### Характеристики

`ProductAttribute` — свободный список: `name` (то, что увидит покупатель: «Склад», «Країна виробництва»), `value`, `position` для порядка. Фиксированного набора полей нет — CRM заводит те характеристики, которые есть у конкретной вещи.

- **чего нет — того не видно**: пустое `value` (или пустое `name`) сайт молча отбрасывает, вместо «Склад: —» просто не будет строки;
- на товар одно значение с данным `name` (`UNIQUE (productId, name)`) — два «Складу» у одной модели означают ошибку импорта, а не два значения;
- порядок на странице = `position`, при равных — по алфавиту;
- три названия сайт понимает особо и отдаёт Google в разметке товара: **Склад / Матеріал / Тканина** → `material`, **Країна виробництва** → `countryOfOrigin`, **Візерунок / Принт** → `pattern`. Регистр неважен. Остальные показываются покупателю, но в разметку не идут.

### Скидки

Одна таблица правил на все три случая:

| `scope`    | На что действует                     | Связь              |
| ---------- | ------------------------------------ | ------------------ |
| `PRODUCT`  | одна позиция или несколько выбранных | `DiscountProduct`  |
| `CATEGORY` | все товары категории                 | `DiscountCategory` |
| `ALL`      | весь каталог                         | —                  |

У правила либо `percent` (1–90), либо `amount` (фиксированная сумма в копейках) — оба сразу база не примет (`CHECK`). Правило действует, пока `isActive = true`; дат начала и конца нет — включается и выключается вручную. Если товар попал под несколько правил, выигрывает то, что даёт покупателю **самую низкую цену**; скидки не складываются.

**Цену со скидкой считает база, а не приложение.** Триггеры пересчитывают `Product.finalPrice` и `ProductVariant.finalPrice` при любом изменении цены, категории или правил — неважно, кто пишет: сайт, CRM или руки в SQL-консоли. Витрина показывает `finalPrice`, зачёркивает `price`, когда `finalPrice < price`, и по `finalPrice` же сортирует и фильтрует «Знижки».

- **не пишите `finalPrice` вручную** — значение перетрётся;
- ручной пересчёт (например, после массовой заливки): `SELECT lily_recompute_prices();`

### Главная страница

Порядок блоков: баннер → категории → «Знижки» → «Новинки» → по ленте на каждую категорию → блок гарантий.

Ленты категорий CRM управляет напрямую, кодом трогать нечего:

- **порядок лент** = `Category.position` (при равных — по имени), тот же, что в каталоге;
- **пустая категория ленты не получает** — считаются только товары, которые реально можно купить (см. «Наличие»);
- в ленте `HOME_CATEGORY_LIMIT` (8) свежих товаров категории; если их больше, под лентой появляется кнопка «Ще N речей у категорії».

Как это грузится:

- первые `HOME_EAGER_SECTIONS` (2) ленты сервер отдаёт прямо в HTML — они почти на первом экране и должны быть в индексе;
- остальные **не существуют в странице, пока до них не догорнули**: `category-feed.svelte` добавляет следующую ленту, когда конец списка подходит к экрану. Поэтому полоса прокрутки в первую секунду показывает высоту того, что реально загружено, а не всего каталога, и растёт вместе с прокруткой;
- добавленная лента сразу просит свои карточки у `GET /api/category/<slug>` и до ответа держит место скелетоном той же высоты;
- заголовок ленты и ссылка на категорию есть в HTML с первой секунды; ссылки на **все** категории — в полосе категорий под баннером, так что перелинковка не зависит от прокрутки;
- фото грузятся лениво все до единого, кроме первого кадра баннера (он LCP). Пока кадр не пришёл, на его месте пульсирует заглушка.

Замерено на продакшен-сборке (1280×900, демо-каталог из 11 категорий): высота при загрузке 4759 px вместо 10988 px, ни одного запроса за товарами до первой прокрутки, CLS за всю прокрутку до низа — 0.0008.

Обе константы — в `src/lib/config.ts`.

### Фото: размеры и вес

Оригиналы в CRM можно заливать какие есть — сайт их не трогает, но и не показывает целиком. Каждый `<img>` просит у CDN кадр ровно той ширины, которая нужна этому месту (`src/lib/image.ts`), плюс `f_auto` — браузер получает AVIF или WebP:

```
оригинал .png                        1 841 154 байт
f_auto,q_auto,c_limit,w_800             45 870 байт
f_auto,q_auto,c_limit,w_400              8 998 байт
```

- работает только для `res.cloudinary.com` (туда льёт CRM) и `images.unsplash.com` (демо-каталог). **Фото с другого хоста отдаётся как есть, во весь вес** — если в CRM появится другое хранилище, добавьте его в `imageSrc`;
- `c_limit` не увеличивает маленький оригинал, так что залить кадр меньше нужного — значит получить мыло: минимум для карточки товара — 720 px по ширине, для баннера — 1920 px;
- **на весь сайт ровно три ширины: 400, 800, 1600** (`IMAGE_WIDTHS` в `src/lib/image.ts`). Это не стиль, а требование: CDN делает уменьшенную копию при **первом** запросе именно этой ширины — 0.8 с против 0.3 с для готовой. Пока он режет, на месте фото серый квадрат. Общие ширины значат, что копия, сделанная для карточки на главной, сразу годится для подсказки в поиске, корзины и кружка категории. **Добавили новую ширину — добавили новую партию серых квадратов**, поэтому новые места берут одну из трёх;
- если CDN не отдал уменьшенный кадр, показывается оригинал (`fallbackToOriginal`) — серого квадрата вместо вещи не будет;
- второе фото карточки (то, что проявляется при наведении) на тач-экранах не рендерится вовсе: наводить нечем, а трафик уходил. Это вдвое меньше фото на сетку — на телефоне 474 КБ против 812 КБ на десктопе;
- `preconnect` к `res.cloudinary.com` стоит в `src/app.html`: рукопожатие с CDN идёт параллельно с разбором страницы.

### Поиск

Ищет только товары — категории в подсказках не показываются (они и так в меню). Движок целиком свой, `src/lib/search.ts`:

- **находит по** названию, категории, цвету варианта, артикулу и описанию — в этом порядке важности;
- **по описанию совпадение строгое** — целое слово или его начало. Поблажливость там даёт глупости: в описании платья есть «з вільною спідницею», и при нестрогом сравнении это платье становилось ответом на запрос «спідниця»;
- **терпит другое окончание**: «сукні» находит «Сукня», «жилетки» — «Жилетка» (совпадение по общему корню, от 4 букв);
- **терпит одну опечатку** в словах от 5 букв: «кутрка» → «куртка»;
- **сводит буквы**, которые пишут одна вместо другой: `и/і/ї/ы`, `е/є/э/ё`, `ґ/г`, мягкий знак и апостроф;
- **все слова запроса должны найтись**: «чорна сукня» не вернёт всё чёрное и все платья.

Почему не полнотекстовый поиск Postgres: для украинского в нём нет стеммера, `to_tsvector` не сводит «сукні» и «сукня» — а это ровно то, что набирает покупатель.

Технически: весь каталог читается из базы **одним запросом** и лежит в памяти разобранным на слова (`src/lib/server/search.ts`, кеш на `CATALOG_CACHE_MS`). Подсказка на каждую букву не идёт в базу вообще. Запрос уходит только когда набрано ≥ `SEARCH_MIN_LENGTH` (2) символа и пальцы остановились на 140 мс; предыдущий запрос отменяется, ответы кешируются в браузере.

**Предел подхода — размер каталога.** Тысячи товаров в памяти нормально, сотни тысяч — нет. Когда каталог дорастёт, `src/lib/server/search.ts` меняется на полнотекстовый поиск в базе; интерфейс (`searchProducts`, `searchProductIds`) остаётся тем же.

Страница `/catalog?q=…` использует тот же движок: он отдаёт id по релевантности, а каталог фильтрует их по размеру и цвету и режет на страницы. Явная сортировка по цене перебивает релевантность.

Чего поиск **не** умеет (если понадобится — дописывать в `search.ts`): синонимов («платье» → «сукня»), исправления раскладки («cerym» → «сукня»), поиска по размеру из таблицы замеров.

### Кеш каталога

Ответы каталога живут в памяти сервера `CATALOG_CACHE_MS` (60 с): главная целиком, ленты категорий и список категорий для шапки. Правка в CRM доезжает на сайт **в течение минуты**.

- корзина, оформление и **страница товара не кешируются** — там решает остаток на складе;
- в `npm run dev` кеш выключен, правки в базе видно сразу;
- кеш в памяти процесса: при рестарте приложения он пуст, при нескольких инстансах у каждого свой.

**HTML-страницы на CDN не кешируются — и не должны.** Перед сайтом стоит CDN Hostinger, и он отдаёт сохранённую копию страницы всем подряд, не глядя на куки. А в шапке каждой страницы зашит счётчик корзины конкретного покупателя: с `s-maxage` на главной человек с тремя вещами в корзине видел ноль или чужие пять — это проверено на живом сайте. Поэтому кешируются данные каталога в памяти процесса, а страница собирается для каждого своя. `s-maxage` допустим только там, где в ответе нет ничего личного: `sitemap.xml`, `robots.txt`, `llms.txt`, фид, `/api/category/*`.

### Наличие

Товар виден в каталоге, поиске и рекомендациях, пока выполняются оба условия: `Product.isActive` и есть хотя бы один вариант с `isActive = true` и `stock > 0`.

- закончился размер — он исчезает из выбора на странице товара;
- закончились все — модель пропадает из списков, но прямая ссылка продолжает открываться с пометкой «Немає в наявності» (сохранённые ссылки и позиции в поиске не ломаются);
- `Product.isActive = false` — страница отдаёт 404;
- позиции в чужих корзинах, ставшие недоступными, пропадают из корзины сами.

## Телеграм-бот: управление заказами

Кроме общей ленты в группе есть бот, который пишет **лично** каждому, кому выдан доступ, и даёт менять статус заказа кнопками под сообщением. Код живёт в `src/lib/server/bot/`, правила переходов — в `src/lib/bot-workflow.ts` (чистый модуль, без базы и сети).

### Как это работает

Новый заказ уходит двумя путями: текстом в группу (как раньше) и персонально каждому активному пользователю бота — уже с кнопками. Нажатие меняет `Order.status`, пишет строку в `OrderEvent` и **переписывает все копии сообщения** во всех чатах: иначе у остальных остались бы кнопки от состояния, которого уже нет.

Маршрут заказа:

```
NEW ──Прийняти──> CONFIRMED ──Відправлено──> SHIPPED ──Отримано──> DELIVERED
 └──────────────── Скасувати ────────────────┴──> CANCELLED
```

Перепрыгнуть шаг или откатить назад нельзя — ни кнопкой, ни подделанным `callback_data`: сервер проверяет переход по той же таблице, из которой рисуются кнопки.

### Роли

| Роль      | Что может                                              |
| --------- | ------------------------------------------------------ |
| `ADMIN`   | всё то же, что менеджер, плюс отчёты и выдача доступов |
| `MANAGER` | весь маршрут, включая отмену                           |
| `COURIER` | только «Отримано» и только у отправленного заказа      |

Кнопки идут столбиком, по одной в строке: в ряд они узкие, и на телефоне «Відправлено» оказывается вплотную к «Скасувати», а цена промаха разная. Отмена помечена знаком `✕` и всегда последняя — **цвет кнопок Telegram задать не даёт**, это ограничение платформы, а не недоделка.

### Доступ: одноразовые коды

Telegram id заранее знать не нужно — человек приносит его сам. CRM создаёт код, человек отправляет боту `/start КОД`, и только в этот момент появляется `BotUser`.

**Что делает CRM:**

```sql
-- Выдать доступ: код можно переслать в любом мессенджере,
-- после первого использования он мёртв.
INSERT INTO "BotInvite" (id, code, role, note, "expiresAt", "createdAt")
VALUES (gen_random_uuid()::text, 'LILY-7K2M', 'MANAGER', 'Олена, склад',
        now() + interval '7 days', now());

-- Кто уже привязался (usedAt заполнен — код израсходован)
SELECT i.code, i.role, i.note, i."usedAt", u.name, u.username
FROM "BotInvite" i LEFT JOIN "BotUser" u ON u.id = i."usedById";

-- Отозвать доступ: действует с первого же касания
UPDATE "BotUser" SET "isActive" = false WHERE id = '...';
```

`expiresAt` можно оставить `NULL` — код будет бессрочным.

Что важно знать про безопасность: отозванному человеку **новый код не поможет**. Строка в `BotUser` остаётся, и повторная привязка того же Telegram id запрещена — иначе отзыв доступа обходился бы выдачей нового кода. Чтобы вернуть человека, снимите отзыв: `isActive = true`.

Тот, кому доступ не выдан, не узнаёт ничего: ни номеров, ни сумм, ни даже того, существует ли такой заказ. На любую команду один и тот же сухой ответ, и запросов к заказам при этом не делается.

### Что читать из базы

| Нужно                   | Откуда                                          |
| ----------------------- | ----------------------------------------------- |
| Текущий статус заказа   | `Order.status`                                  |
| История: кто и когда    | `OrderEvent` (`status`, `actorId`, `createdAt`) |
| Список людей с доступом | `BotUser`                                       |
| Выданные коды           | `BotInvite`                                     |

`OrderEvent.actorId` — это `BotUser.id`. `NULL` означает, что статус поменяли не из бота.

### Синхронизация с CRM

**Статус может менять и CRM** — бот это переживает и, более того, сам подстраивается.

Сообщение в чате показывает то состояние, которое было на момент отправки. Если статус поменяли в CRM, кнопки под ним устаревают. Раньше нажатие по такой кнопке просто отвечало отказом, и заказ в чате застревал навсегда. Теперь нажатие **перерисовывает карточку** под настоящее состояние: менеджер видит актуальный статус и актуальные кнопки, и следующим касанием продолжает работу. Сам статус при этом не меняется — заказ не должен прыгать назад из-за промаха.

Синхронизация ленивая, по нажатию. Опрашивать базу на случай, что CRM что-то изменила, пришлось бы постоянно и вхолостую, а заказ читается и так — в момент, когда по нему нажали.

Настоящий отказ от устаревшей карточки отличается по одному признаку: могла ли эта роль когда-либо сделать такой переход. Курьеру «Скасувати» не давали ни в одном состоянии — значит, данные кнопки подделаны, и это отказ. Менеджер, нажавший «Прийняти» на уже отправленном заказе, нажал настоящую кнопку — просто карточка отстала.

**Если CRM меняет `Order.status`** — добавляйте заодно строку в `OrderEvent` с `actorId = NULL`, иначе история станет дырявой и в карточке не будет подписи «кто изменил». Перетереть чужое изменение бот не может: он меняет статус условным `UPDATE ... WHERE status = <ожидаемый>`.

**Отмена возвращает товар на склад.** Остатки списываются при оформлении, и без возврата отменённый заказ тихо съедал бы склад. Возврат идёт в той же транзакции, что и смена статуса, — иначе между ними можно было бы упасть и оставить склад рассинхронизированным. Позиции без `variantId` пропускаются: вариант могли удалить в CRM уже после заказа, возвращать некуда.

### Закрытый заказ исчезает из чата

Как только заказ получен или отменён, карточка удаляется из всех чатов, где она висела, а строки `BotNotice` убираются из базы. По закрытому заказу делать нечего, а в переписке он остаётся навсегда и вытесняет живые.

Отправленный заказ не трогается: по нему ещё отмечают доставку, и кнопка «Отримано» должна остаться под рукой.

Что считать закрытым, выводится из той же таблицы переходов, из которой рисуются кнопки, — это состояние, из которого некуда двигаться. Отдельного списка нет намеренно: два списка рано или поздно разошлись бы.

**Аналитика не страдает.** История целиком лежит в `OrderEvent` и остаётся на месте. `BotNotice` помнил только, в каком чате и под каким id лежит сообщение, — без самого сообщения эта строка ни о чём.

Два ограничения, о которых стоит знать:

- Telegram разрешает боту удалять свои сообщения **только первые 48 часов**. Заказ, закрытый позже, стереть уже нельзя — такая карточка сворачивается в одну строку без кнопок: `LL-ABC234 · Доставлене`.
- Если заказ закрыли в CRM, карточка исчезнет не сразу, а при первом нажатии по ней — по той же ленивой синхронизации, что описана выше.

Для CRM отсюда следует одно: **не опирайтесь на `BotNotice` как на признак чего-либо.** Строки этой таблицы живут ровно столько, сколько сообщение висит в Telegram. Источник истории — `OrderEvent`.

### Настройка

1. `TELEGRAM_WEBHOOK_SECRET` в `.env` и в переменных хостинга — общий секрет с Telegram. Без него бот выключен, а роут вебхука отвечает 404. Сгенерировать: `node -e "console.log(crypto.randomUUID())"`.
2. `npm run telegram:webhook` — зарегистрировать адрес. Нужен публичный HTTPS, локальный сервер не подойдёт.
3. `npm run telegram:webhook -- --status` — проверить состояние: очередь событий и последнюю ошибку доставки.

Команды бота: `/start КОД`, `/zamovlennia` (активные заказы), `/z LL-XXXXXX` (найти по номеру), `/dopomoha` (подсказка), `/vyity` (выйти).

Владельцу (`ADMIN`) дополнительно: `/zvit` — отчёт (заказы по статусам, выручка за сутки и за неделю, сколько ждёт обработки), `/dostup` — список людей с доступом, `/kod РОЛЬ примітка` — выдать код не заходя в CRM, `/vymknuty ID` и `/uvimknuty ID` — закрыть и открыть доступ.

Команд, которых человеку не видно, для него не существует: менеджер, набравший `/zvit`, получает обычную подсказку, а не «вам это недоступно» — второе уже сообщает, что отчёт где-то есть.

**Список команд ставится в меню Telegram** — та самая кнопка слева от поля ввода. Список свой на каждый чат и зависит от роли, поэтому менеджер не видит команд владельца. Ставится он в момент погашения кода (раньше роль неизвестна) и убирается при выходе.

### Выход из бота

`/vyity` — человек уходит сам. Заказы перестают приходить, меню команд убирается, вернуться можно только новым кодом: старый давно погашен.

Отличие от отзыва владельцем хранится в `BotUser.leftAt`. Ушедший сам может вернуться по новому коду — при этом обновляется прежняя строка, а не создаётся новая, так что журнал `OrderEvent` не теряет связь с человеком. Тому, кого выключил владелец (`isActive = false`, `leftAt` пустой), новый код не поможет — иначе выключатель обходился бы в два сообщения.

### Что сделано ради безопасности

- **Только личный чат.** В группе бот молчит совсем. Это не удобство: в группе `chat.id` — это группа, и сработай там `/start`, доступ привязался бы к ней, а все заказы магазина поехали бы в чат, где сидит кто угодно.
- **Подбор кода бессмыслен.** Пять ошибок подряд — и десять минут молчания. Отклонённая попытка не стоит ни одного запроса в базу. Сам код — шесть символов из 32-символьного алфавита, то есть миллиард вариантов.
- **Отозванного не вернуть чужим кодом.** Строка в `BotUser` остаётся, повторная привязка того же Telegram id запрещена — иначе выключатель в CRM ничего бы не значил.
- **Себя владелец выключить не может** — иначе запрёт сам себя снаружи, и открыть доступ будет некому.
- **Ответы неразличимы.** Несуществующий код, использованный и просроченный отвечают одинаково; посторонний не узнаёт даже, существует ли заказ с таким номером.
- **Авторизация не кешируется.** Один индексированный запрос на каждое нажатие — сознательный выбор: кеш означал бы, что отозванный доступ живёт ещё сколько-то секунд.

### Нагрузка на базу

Отчёт — три агрегата параллельно (`groupBy` по статусам и два `aggregate` по суммам), сами заказы в память не выбираются. Проверка доступа — один запрос по уникальному индексу. Нажатие кнопки читает заказ **ровно один раз**: после успешного перехода новое состояние и так известно, так что карточка перерисовывается из уже прочитанного, а не вторым запросом. Таблица `BotUpdate` не растёт вечно: записи старше суток удаляются, и не по расписанию, а изредка прямо в вебхуке (примерно раз на пятьсот событий) — ради одной таблицы отдельный планировщик не нужен.

### Засыпание хостинга

Отдельного «будильника» не нужно: запрос от Telegram сам поднимает процесс. Опасность в другом — на ответ кнопке у Telegram около 15 секунд, и если холодный старт дольше, у менеджера крутится часик и вылезает «query is too old», хотя статус в базе поменяется.

Поэтому бот отвечает на нажатие **до** похода в базу. Потерять событие всё равно нельзя: Telegram повторяет доставку, а повторы гасятся таблицей `BotUpdate` по `update_id` — одно нажатие не переведёт заказ через два состояния. Если холодные старты станут заметны, самое дешёвое лечение — внешний пинг раз в 5–10 минут.

## SEO

Проверено Lighthouse на живых данных: SEO, доступность и лучшие практики — **100** на главной, категории, товаре и страницах условий.

**Разметка Schema.org.** Собирается на сервере в `src/lib/server/seo.ts`, вставляется одним тегом в `<head>` через `hooks.server.ts` (страницы кладут узлы в `locals.jsonLd`). В Svelte нельзя отдать `<script>` из шаблона без `{@html}`, а это дыра под XSS — поэтому вставка живёт в хуке, а JSON экранируется так, что закрывающий тег в нём физически не появится.

| Страница          | Что отдаётся                                            |
| ----------------- | ------------------------------------------------------- |
| Все               | `OnlineStore` (гео: Украина, UAH) + `WebSite` с поиском |
| Товар             | `ProductGroup` с вариантами + `BreadcrumbList`          |
| Категория         | `ItemList` + `BreadcrumbList`                           |
| Доставка, возврат | `BreadcrumbList`                                        |

Карточка товара в выдаче требует цену, наличие, артикул, доставку и условия возврата — всё это берётся из базы и `config.ts`, ничего не выдумывается. Рейтингов и отзывов в разметке нет, потому что их нет в магазине: за фиктивные Google снимает карточки целиком.

- **Скидка** уходит в разметку как `StrikethroughPrice` — Google может показать зачёркнутую цену прямо в карточке. Только если товар и правда продаётся со скидкой; вариант со своей ценой старую цену товара не наследует.
- **Условия возврата** ссылаются на `/returns` (`merchantReturnLink`) — без страницы с условиями Merchant Center политику не принимает.

**Индексация.** Страницы с фильтрами (`?size=`, `?color=`) и поиск (`?q=`) отдают `noindex, follow` и канонический адрес без параметров — иначе в индекс попадают тысячи почти одинаковых URL. `?sale=1` и `?page=N` индексируются: это разный контент. Корзина, оформление, страница заказа и страница ошибки закрыты `noindex`.

**Пустая категория** (в CRM она есть, а товаров нет) отдаёт `noindex` и пропадает из меню в шапке и подвале. Google такие страницы считает «мягкой 404» и снижает доверие ко всему сайту. Появится товар — категория вернётся сама.

**Тексты категории.** Заголовок — «Жіночі демісезонні куртки — купити в Україні», а не голое «Демісезонні куртки»: так категорию и ищут. Под `h1` — абзац с фактами: сколько моделей, от и до скольки стоят, сроки и цена доставки. Всё считается из базы на лету. Описания главной и `/catalog` тоже собираются из реальных категорий — зашитые «сукні й трикотаж» врали бы, как только их разобрали.

**Подписи фото.** В CRM поле `alt` иногда заполняют заглушками — в живом каталоге было 37 фото с «Тест», «Тест2», «NBoy». Сайт берёт подпись из CRM, только если в ней хотя бы два слова и это не заглушка; иначе собирает «Название — цвет» (`imageAlt` в `src/lib/product-images.ts`). Чинить в CRM всё равно стоит, но покупатель и Google мусора уже не видят.

### Для поисковиков и ИИ

| Адрес                | Для кого                             | Что внутри                                              |
| -------------------- | ------------------------------------ | ------------------------------------------------------- |
| `/sitemap.xml`       | Google, Bing                         | Страницы + фото каждого товара (`image:image`)          |
| `/robots.txt`        | все роботы                           | Что закрыто от индекса, ссылка на карту                 |
| `/merchant-feed.xml` | Google Merchant Center, каталог Meta | Каждый размер и цвет — отдельная позиция с фото и ценой |
| `/llms.txt`          | ChatGPT, Gemini, Perplexity и др.    | Категории, цены, условия, все товары — со ссылками      |
| `/delivery`          | покупатели, Merchant Center, ИИ      | Способы доставки, цены, сроки, оплата                   |
| `/returns`           | покупатели, Merchant Center, ИИ      | Срок, условия и порядок возврата                        |
| `/contacts`          | покупатели, Merchant Center          | Телефон, почта, Instagram, самовывоз                    |

Всё собирается из базы и `config.ts`, поэтому цены и условия везде одни и те же. Формулировки условий живут в одном месте — `src/lib/store-facts.ts`: если бы каждая страница писала «90 грн» сама, рано или поздно в `llms.txt` осталась бы старая цена, и ассистент уверенно пересказал бы её покупателю.

**Фид Merchant Center.** Фото в нём и в `og:image` — в JPEG (`portableImageSrc`), а не `f_auto`: часть фото в каталоге залита в AVIF, а Merchant Center AVIF не принимает, и позиция вылетела бы из Google Покупок. Фото позиции — того цвета, который в ней продаётся.

**Заголовки безопасности** ставит `hooks.server.ts` на каждый ответ: запрет встраивать сайт в чужой `<iframe>` (защита оформления от подделки поверх), `nosniff`, HSTS. Полной CSP нет сознательно — объяснение в самом хуке.

**Что нужно сделать вручную после запуска:**

1. **Заменить заглушки в `src/lib/config.ts`**: `SITE.phone`, `SITE.email`, `SITE.instagram`, `SENDER.pickupAddress`. Они уходят в подвал, на `/contacts`, в разметку магазина и в `llms.txt` — сейчас там `+38 (067) 000-00-00` и `hello@lilylook.ua`, хотя домен `.store`.
2. **Google Search Console**: подтвердить домен, отправить `/sitemap.xml`.
3. **Google Merchant Center**: добавить фид `https://lilylook.store/merchant-feed.xml` (расписание — раз в день), указать страницу возврата `/returns`, настроить доставку по Украине. Без этого товары в Google Покупки и в товарные карточки выдачи не попадают.
4. **Bing Webmaster Tools**: отправить тот же `/sitemap.xml`. Поиском Bing пользуются ChatGPT и Copilot — без него магазин туда не попадает.
5. **В CRM**: поправить подписи фото с «Тест»/«NBoy» и размер `4ХL`, набранный кириллической «Х».

### Иконки

Лежат в `static/`, подключены в `src/app.html`. Именно `static/`, а не `src/lib/assets/`: Vite хеширует имена импортированных файлов, а браузеры и iOS запрашивают `/favicon.ico` и `/apple-touch-icon.png` наугад, по корневому адресу.

| Файл                             | Кто использует                                  |
| -------------------------------- | ----------------------------------------------- |
| `icon.svg`                       | вкладка в современных браузерах (любой масштаб) |
| `favicon.ico`                    | запасной вариант; внутри 16/32/48               |
| `apple-touch-icon.png` (180×180) | ярлык на домашнем экране iOS                    |
| `android-chrome-192/512.png`     | Android через `site.webmanifest`                |

`android-chrome-512x512.png` уходит ещё и в `logo` узла `OnlineStore` — Google берёт его в панель знаний. Меняете иконку — меняйте этот файл, адрес в разметке привязан к имени.

Отдельные `favicon-16x16.png` / `favicon-32x32.png` не нужны: те же размеры уже внутри `.ico`.

**Изменить схему БД:** правишь `prisma/schema.prisma` → `npm run db:migrate` → при необходимости обновляешь view-модели в `src/lib/types.ts`.

## Деплой

Собирается через `@sveltejs/adapter-node` — на выходе обычный Node-сервер в `./build`. Он подходит и Hostinger, и любому VPS, и Vercel/Netlify (там достаточно указать команду запуска).

```bash
npm ci
npm run db:deploy     # применить миграции (нужен DIRECT_URL)
npm run build         # svelte-kit sync → prisma generate → vite build
npm start             # = node build, слушает $PORT
```

Готовый сервер кладётся в `build/` (`adapter.out` в `svelte.config.js`) — это же имя стоит в поле «Каталог виводу» у хостинга. Меняется в двух местах сразу: `svelte.config.js` и скрипт `start`; они всегда должны совпадать с настройкой площадки, иначе деплой отвечает `No output directory found after build`.

Переменные окружения площадки: `DATABASE_URL` (pooled), `DIRECT_URL` (direct, для миграций), `PUBLIC_SITE_URL`, при необходимости `NOVA_POSHTA_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`. Читаются в рантайме (`$env/dynamic/private`), пересборка при их смене не нужна.

**`ORIGIN` обязателен за обратным прокси.** Хостинг проксирует запросы на localhost, и adapter-node видит хост `localhost`, а не домен. Без `ORIGIN=https://ваш-домен` любая отправка формы (добавить в корзину, оформить заказ) отлетает с `Cross-site POST form submissions are forbidden`. Альтернатива, если прокси корректно ставит заголовки: `PROTOCOL_HEADER=x-forwarded-proto` и `HOST_HEADER=x-forwarded-host`.

### Hostinger (Node.js web app)

Сайт должен быть заведён как **веб-приложение Node.js**, а не как обычный хостинг с `public_html`: во втором случае папку отдают статикой, `index.html` в ней нет, и домен возвращает `403 Forbidden`. Поля в hPanel:

| Поле                  | Значение                                                  |
| --------------------- | --------------------------------------------------------- |
| Framework             | SvelteKit (в списке backend-фреймворков)                  |
| Node.js version       | 22.x                                                      |
| Build command         | `npm run build`                                           |
| Output directory      | `dist`                                                    |
| Entry file            | `index.js` (то есть `dist/index.js`)                      |
| Environment variables | `DATABASE_URL`, `DIRECT_URL`, `PUBLIC_SITE_URL`, `ORIGIN` |

Если площадка ждёт другое имя папки — поменяй `adapter({ out: … })` в `svelte.config.js` и `start` в `package.json`; обе строки должны совпадать с полем Output directory.

Конфигурация SvelteKit — в `svelte.config.js` (адаптер, `out: 'build'`). Держать её там, а не инлайном в `vite.config.ts`, важно по двум причинам: инлайн-объект в `sveltekit({...})` полностью заменяет этот файл, и сборщики хостингов (Hostinger в их числе) ищут папку сборки именно через него.

**Порядок в `build` важен.** `prisma generate` читает корневой `tsconfig.json`, а тот наследует `./.svelte-kit/tsconfig.json` — файл, которого на свежем клоне ещё нет. Поэтому первым идёт `svelte-kit sync`; если поменять порядок местами, сборка на хостинге упадёт с `Could not resolve '../../../prisma/generated/client.js'`.

**Edge-рантайм.** Сейчас используется `@prisma/adapter-pg` поверх TCP — это работает в Node-рантайме (Vercel Functions, Netlify, Node-сервер). Если понадобится edge, замени адаптер на `@prisma/adapter-neon` (WebSocket) в `src/lib/server/db.ts` — это изменение в одном файле.
